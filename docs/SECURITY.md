# Security

Schedaro uses a dedicated PostgreSQL container, database (`schedaro_db`), application user (`schedaro_app`), network, and named volume. Keep these resources isolated and use fresh local credentials.

Secrets live only in private `.env` and are excluded from build contexts. `.env.example` contains placeholders. The database is not exposed on a host port. Backend CORS is limited to the development frontend origin; production origins must be explicit.

FastAPI/Pydantic validates request values, SQLAlchemy uses parameterized operations, and resource ownership checks reject cross-institution or cross-department academic assignments. PostgreSQL foreign keys, check constraints, unique constraints, and exclusion constraints protect relational and concurrent scheduling consistency. Stage 4 uses inactive lifecycle flags instead of destructive deletion for records that may be referenced by timetable sessions. Rust receives normalized values only and has no database access or credentials.

Stage 7A adds a central `schedaro_platform` database and an idempotent, interactive `python -m app.bootstrap_owner` command. It refuses production bootstrap, requires a 12-character password, stores only scrypt hashes, creates one server-side session hash, and sets an HttpOnly SameSite cookie. `/api/v1/auth/*` and `/api/v1/platform/*` enforce authentication/Platform Owner authorization; academic, timetable, generation and print routes reject unauthenticated requests. Tenant database names are resolved only from the central registry and validated before SQLAlchemy engine creation; arbitrary URLs and browser-provided connection strings are rejected. `python -m app.provision_tenant` is a development-only isolated database initializer with safe identifier validation.

The current Stage 7A limitation is explicit: the existing academic schema still contains legacy institution IDs in the preserved `schedaro_db`, so owner support access is registry-authorized but not yet a complete membership-scoped ordinary-user model. MFA, CSRF protection for a production deployment, rate limiting, and full per-route tenant-session routing remain required before production release. Public write APIs still require operation-level authorization, rate limiting, and audit review before deployment. The public source repository is not a public writable backend.

Automatic generation is bounded to a maximum of 12 class groups and 30 seconds per request, uses one CP-SAT worker, and does not execute user-supplied code. Generated proposals are institution/term scoped, independently Rust-validated, and rechecked against current PostgreSQL rows before a transaction can add sessions. Public deployment still requires authentication, authorization, rate limiting and job governance for write-heavy generation endpoints. Future AI requests must minimize data, obtain user approval, and document privacy/retention behavior. Never log passwords, connection strings, or scheduling payloads containing private notes.

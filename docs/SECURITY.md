# Security

Schedaro uses a dedicated PostgreSQL container, database (`schedaro_db`), application user (`schedaro_app`), network, and named volume. Keep these resources isolated and use fresh local credentials.

Secrets live only in private `.env` and are excluded from build contexts. `.env.example` contains placeholders. The database is not exposed on a host port. Backend CORS is limited to the development frontend origin; production origins must be explicit.

FastAPI/Pydantic validates request values, SQLAlchemy uses parameterized operations, and resource ownership checks reject cross-institution or cross-department academic assignments. PostgreSQL foreign keys, check constraints, unique constraints, and exclusion constraints protect relational and concurrent scheduling consistency. Stage 4 uses inactive lifecycle flags instead of destructive deletion for records that may be referenced by timetable sessions. Rust receives normalized values only and has no database access or credentials.

Stage 7A adds a central `schedaro_platform` database and an idempotent, interactive `python -m app.bootstrap_owner` command. It refuses production bootstrap, requires a 12-character password, stores only scrypt hashes, creates one server-side session hash, and sets an HttpOnly SameSite cookie. `/api/v1/auth/*` and `/api/v1/platform/*` enforce authentication/Platform Owner authorization; academic, timetable, generation and print routes reject unauthenticated requests. Tenant database names are resolved only from the central registry and validated before SQLAlchemy engine creation; arbitrary URLs and browser-provided connection strings are rejected. `python -m app.provision_tenant` is a development-only isolated database initializer with safe identifier validation. If the local owner already exists and its password is unavailable, `python -m app.reset_owner` performs an explicit interactive reset only in non-production, requiring the existing owner email, a `RESET` confirmation, and two hidden password prompts; it never creates a duplicate or accepts a password argument.

Stage 7B onboarding remains Platform Owner-only through server-verified session role checks. Browser names, codes and labels never become SQL identifiers; database names are generated from a server UUID and validated before PostgreSQL `CREATE DATABASE`. Provisioning uses a persisted idempotency key and explicit `provisioning` → `ready`/`provisioning_failed` states. Failures retain safe truncated diagnostics, and retry does not delete or recreate a tenant database. Connection strings and credentials never appear in platform responses. Stage 7C adds stable `/c/{slug}` public branding contexts, central invitation and password-recovery records, hashed single-use expiring token verifiers, central College Administrator memberships and a persisted local-development email capture. Stage 7C.1 adds manual activation URLs containing only nonsecret invitation IDs and separate high-entropy keys; only key digests are stored, keys expire and are consumed once, and manual redemption creates an inactive membership pending owner approval. Raw invitation/recovery secrets are not returned by list APIs or written to audit events. Existing-account public invitation activation refuses to claim the identity rather than changing its password. Portal slugs are never database identifiers and do not grant access; protected academic access requires a server session and membership. Stage 7D adds explicit role assignments, delegation checks, scope validation and server-side acting-as context; Platform Owner grants remain protected and revocation clears matching session context. Stage 7E/7F workflow authorization adds role-scoped draft creation, creator self-review denial, separate review/publication permissions and published-only student retrieval. Full legacy child-record permission enforcement, editor-to-version synchronization, configurable approval-policy administration, CSRF protection, login rate limiting, authenticated existing-user attachment and external SMTP delivery remain outstanding before production. Local synthetic fixtures and reset commands are development-only, explicitly allow-listed, require non-production configuration, preserve platform users, and do not expose generated credentials.

Manual password recovery is a central-account operation. The Platform Owner may issue a development-only one-time manual reset key for an existing non-owner account through the protected Users & Access action or `python -m app.manual_reset`; ordinary institution roles cannot issue these keys, and the Platform Owner uses its separate protected recovery workflow. The key is generated from 256 bits of cryptographically secure randomness, stored only as a SHA-256 verifier, expires by default after 30 minutes, is displayed only in the issuance response, and is consumed atomically. Manual and email recovery update the same central password hash and revoke the account's sessions. Invalid recovery digests receive bounded database-backed attempt throttling; reset audit records contain identifiers and method metadata, never plaintext keys. Recovery changes credentials only: it does not activate memberships, verify email, or change roles/scopes.

The current Stage 7A limitation is explicit: the existing academic schema still contains legacy institution IDs in the preserved `schedaro_db`, so owner support access is registry-authorized but not yet a complete membership-scoped ordinary-user model. MFA, CSRF protection for a production deployment, rate limiting, and full per-route tenant-session routing remain required before production release. Public write APIs still require operation-level authorization, rate limiting, and audit review before deployment. The public source repository is not a public writable backend.

Automatic generation is bounded to a maximum of 12 class groups and 30 seconds per request, uses one CP-SAT worker, and does not execute user-supplied code. Generated proposals are institution/term scoped, independently Rust-validated, and rechecked against current PostgreSQL rows before a transaction can add sessions. Public deployment still requires authentication, authorization, rate limiting and job governance for write-heavy generation endpoints. Future AI requests must minimize data, obtain user approval, and document privacy/retention behavior. Never log passwords, connection strings, or scheduling payloads containing private notes.
